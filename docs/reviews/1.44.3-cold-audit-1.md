# Cold audit 1: tapiOca server 1.44.3, "Sign out always takes you off the list"

Before integration, by an independent auditor who hadn't seen it built
(October 29, 2026). Its report as given, then what was done about each
finding.

**What it read.** The release, `wip/signout-ends`, `33cacfc..7da13e8`: seven
commits, six of them this design's, the seventh (`8e4d459`) the new release
signing key and the gates' output change. The design: the server's
`docs/threat-models/signout-ends.md`, against the audited record in the
apps' repository (its threat model, third version) and its three design
audits. The base for the failing-first check: `573db0f`.

**How it checked.** "Observed" means run; "reasoned" means read, not run.
Two scratch worktrees, both removed; neither checkout changed.

**What it ran (observed):** the requested pytest set (553 passed);
`python3 -m tools.attack_check` (825 of 825); `python3 tools/upgrade_check.py
--from v1.44.2` (114 passed); `ruff check app` (clean);
`tests/test_info_station.py` and `tests/test_release_workflow.py` (77
passed); `tools/release_gate.py lint`, `tools/dupes.py`,
`tools/size_ratchet.py` and `tools/claude_rules.py` (all pass). Two ruff
errors outside `app/` were there before this release.

## Verdict

**No P0. One P1 (SO-C1-01): the proof the record promises isn't all there.**
The code does what the design says on every path tried, with no way found to
take another person off a list, keep a sign-in alive, or reach anything else
through the opened route. **Integrate once SO-C1-01 is fixed**, with SO-C1-02
and -03 in the same round; the final-diff audit re-checks SO-C1-01 to -03.

## Findings

### SO-C1-01 (P1, proof): the proof plan and FG-09's "every path" aren't met

1. Rows of §4 with no test: P4 (a new PIN, a PIN removed, Full sign-in), P6
   (the 21st sign-in), P7 (an Admin ending it by ID, a trusted network
   forgotten, pruned), P17 (gone from `sessions` before the update) and R2 (a
   remove racing a pick). Observed by probes: P6 and P7 answer 200 and remove
   the person; the behavior is right but unproved.
2. The no-meta test never reaches the rule: its file has no `device_sign_ins`
   table, so `changes_needed` never asks it (a spy recorded no call), and it
   passes on 1.44.2's code.
3. "changes_needed and _upgrade agreeing on every case" is tested only on the
   pure predicate, not through its two callers, which work out its inputs
   differently. Observed on 24 real files: they agree in all 24; the suite
   doesn't prove it.
4. P21's test sends `Bearer anything` and doesn't assert the rows unchanged.
5. R3's test doesn't assert the password's answer, that the new sign-in can't
   list the person again, or that its worker finished.

**Fix:** tests for each; the agreement on real files; the no-meta file with
the table; P21's rows asserted with a real sign-in; R3 tightened.

### SO-C1-02 (P2, startup performance): the start's check is quadratic in `sessions`, and runs twice

The newest-sign-in query was a correlated subquery per sign-in, browsers'
included, with no index on `device_id`. Observed: 0.012 s at 200 sessions,
0.079 s at 1,000, 4.2 s at 10,000, about 110 s at 50,000; `Database()` pays
the same again. **Fix:** a window function over the sign-ins with a device
(observed: 0.002 s at 10,000), in the fill and the check; correct FG-07.

### SO-C1-03 (P2, census): "only the remove reads the table" was pinned per file

The census only checked that `db.py` was the one file naming the table; a new
`Database` method reading it, called from any route, would pass. **Fix:** an
AST census of `db.py` pinning the names allowed to mention it; the server's
copy of the record to say the same.

### SO-C1-04 (P3, update): a start that keeps failing before `note_version` backs up and rebuilds at every restart

`version_started` is written late in the lifespan, so a restart loop repeats
the backup and rebuild, losing rows of sign-ins gone from `sessions`, and
after three restarts the copy from before the update is pruned (every copy
left still opens under 1.44.2). **Fix:** write it into the known limits, or
record what the rebuild answered for.

### SO-C1-05 (P3, restore): a restored backup can keep stale rows

A backup made by a version before 1.34.0, or an unreleased build, of an
updated database brings rows and a `version_started` the rule can't read as
old, and backups hold no `sessions` for the unrowed check. **Fix:** empty the
table as a restore puts the backup in place, as alerts are.

### SO-C1-06 (P3, going back from a later version): a reshaped table stops 1.44.3 at start

Observed with the column renamed: `changes_needed` raised, and tapiOca would
stop. **Fix:** a line in the record (later versions add columns and never
rename them), or rebuild a table of the wrong shape.

### SO-C1-07 (P3, release signing, in `8e4d459`): the old key is trusted for every version, and the plan's rule isn't updated

The README's `allowed_signers` lists both keys under one principal, with no
limit by version; the plan says a new key ships in an image before it's used,
with a revocation list. **Fix:** the old key's signature to count only for
1.44.2; the owner deletes the archived repository's signing secret; the
exception in the plan's text with its decision; the key change named in
1.44.3's notes.

### SO-C1-08 (P3, words and docs)

`docs/internal-api.md`'s new text called every API token a 403 (an unknown
one is 401), never said the person must still be on the list, and was hard to
read. The open list's reason said "a sign-in of yours there, still good"
(a live sign-in of any device works). The manifest's "every backup tapiOca
makes" (1.44.2's hold rows). The server's record dropped part of rule 3,
FG-10's "no playback touched" wasn't quite right, and "stops being taken"
reads better as "stops working".

### SO-C1-09 (P3, no slop)

An unused column (`made_ms`); "the table is new, so fill" decided twice; an
unreachable fallback in the handler; `on_picker` called under the database's
lock with nothing saying it must read nothing; and in the tests a line that
does nothing, imports inside functions, and an assertion's redundant half.

### SO-C1-10 (P3, process): 573db0f's "failing first" overstated two tests

With the final test file on `573db0f`'s code, P11b and P1b fail for the
reason the fix changes, so the two setup corrections (88f6435) weakened
nothing. But their first setups couldn't have passed on any code, so the
claim wasn't checked for those two. **Fix:** run each failing-first test
against the old code and read why it fails before saying so.

## What holds (checked)

- No path takes another person off a list: each row is written for its
  sign-in's own person; "renewed from" is the password route's own sign-in;
  the lookup is filtered by this device.
- Nothing keeps a sign-in alive: the ended path never notes it seen and never
  makes a sign-in.
- The Gate change only adds: a live sign-in reaches the remove as before;
  the kept refusal is per request; cookie and Bearer are told apart by one
  function in both places.
- R1 to R3 are under one lock and one transaction; the rebuild is one
  transaction with its mark.
- A database error answers the bare 500.
